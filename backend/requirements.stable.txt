# Pinned dependency set for the STABLE DSPy line (dspy==3.3.1) on the pip
# install path. Pairs DSPy 3.2.1 with gepa==0.1.4 — newer than the gepa==0.0.27
# that DSPy 3.2.1 pins by default — because the react /run tool-optimization
# needs gepa's enable_tool_optimization adapter (a 0.1.x feature) and GEPA PxN
# batched sampling (gepa.strategies.proposal_sampling, new in 0.1.4) that the
# shared optimizer source imports at module load. dspy 3.2.1 runs cleanly
# against gepa 0.1.4 at runtime (verified), but its metadata still
# hard-pins gepa==0.0.27, so install this lockfile with --no-deps — a resolving
# install fails with ResolutionImpossible. backend/Dockerfile's pip path does
# exactly that. The agent layer bridges classic ReAct vs ReActV2 in
# core.service_gateway.react_compat, so the same source runs on either line.
# The DEFAULT line (dspy 3.3.0) lives in requirements.txt.
#
# prometheus-fastapi-instrumentator stays on 8.0.2 in both lines because 7.x
# caps Starlette below 1.0. install_metrics() in core.api.observability uses the
# Instrumentator(...).instrument().expose() API shared by 8.x releases.
#
# Regenerate after changing dependencies. --universal is load-bearing: without
# it the compile resolves for the current machine and can drop packages needed
# by the Linux image.
#    uv pip compile pyproject.toml --no-header --universal \
#        --override <(printf 'dspy==3.2.1\ngepa==0.1.4\nprometheus-fastapi-instrumentator==8.0.2\n') -o requirements.stable.txt
#
# pip check against this line reports only the intentional DSPy/GEPA metadata
# mismatch described above; CI rejects every other dependency problem.
